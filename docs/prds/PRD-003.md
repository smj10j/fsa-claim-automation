# PRD-003: Navia Benefits Form Auto-Fill

**Status**: `draft`
**Priority**: P0
**Effort**: L (1–2 weeks)
**Dependencies**: PRD-001, PRD-002
**Last updated**: 2026-03-18

---

## Problem

The Navia Benefits claim portal requires users to manually enter the same information the extension already knows: merchant name, service date, expense type, amount, and attach a receipt. For 10+ claims this takes 20–30 minutes and is the #1 pain point that causes users to give up and forfeit FSA funds. The extension must eliminate this manual data entry entirely.

---

## Goals

1. Navigate to the Navia Benefits claim submission portal and auto-fill each claim form field using data from the scanned orders.
2. Attach the captured invoice screenshot automatically.
3. Pause before final submission so the user can review and confirm each claim.
4. Handle Navia's React-based SPA without breaking on route changes.

## Non-Goals

- Auto-submitting without user review (always require a human confirmation click)
- Support for other FSA providers (see PRD-007)
- Handling dependent care or medical expense reimbursements beyond OTC/products

## Functional Requirements

### FR-1: Claim Generation
- Map each approved `AmazonOrder` → `Claim` object:
  - `merchantName`: "Amazon.com"
  - `serviceDate`: order date
  - `expenseType`: derived from eligibility category (e.g., "Medical Equipment", "OTC Drug")
  - `amount`: order total (or per-item amount if multi-item split is needed)
  - `invoiceDataUrl`: from `invoice:{orderId}` storage key
  - `claimantName`: pulled from Navia portal profile (scraped on first run)
- Store generated `Claim[]` in `AppState.claims`.

### FR-2: Portal Navigation
- Service worker opens `navia.com` claim submission URL in a tab.
- Content script (`form-filler.ts`) detects the current form state via `form-observer.ts`.
- If user is not logged in, emit `NAVIA_AUTH_REQUIRED` and prompt user to log in manually.

### FR-3: Form Field Filling
- Fill all required fields:
  - "Date of Service" → `serviceDate`
  - "Expense Type" / category dropdown → `expenseType`
  - "Merchant / Provider Name" → `merchantName`
  - "Amount" → `amount`
  - "Patient / Claimant" → `claimantName`
- Use proper React synthetic event dispatch (`Object.getOwnPropertyDescriptor` + `InputEvent`) to trigger React's onChange handlers — standard `.value =` assignment does not work.
- After filling, verify each field's value matches expected (re-read DOM).

### FR-4: Invoice Attachment
- Convert stored `dataUrl` (PNG base64) to a `File` object.
- Programmatically attach to the portal's file input using `DataTransfer`.
- Verify attachment appears in the portal UI before proceeding.

### FR-5: User Review & Confirmation
- After form is filled, extension sends `CLAIM_READY_FOR_REVIEW` to popup.
- Popup shows a "Review Claim" card with all filled values and an invoice thumbnail.
- User clicks "Submit" or "Skip" in the popup.
- On "Submit": content script clicks the portal's submit button.
- On "Skip": content script clears the form, moves to next claim.

### FR-6: Submission Confirmation
- After submit click, `form-observer.ts` watches for success/error state:
  - Success: confirmation message or redirect → emit `CLAIM_SUBMITTED`.
  - Error: validation error toast/message → emit `CLAIM_SUBMIT_FAILED` with error text.
- Service worker updates `Claim.status` in storage accordingly.

### FR-7: Multi-Claim Batching
- After one claim submits, automatically navigate to "New Claim" and start the next.
- Continue until all approved claims are processed or user pauses.
- Show progress: "Claim 3 of 7 submitted" in popup.

### FR-8: SPA Navigation Handling
- `form-observer.ts` uses `MutationObserver` to detect Navia's SPA route changes.
- Re-initializes form-filler context after each navigation.
- Handles multi-step claim forms (some providers use wizard flows).

## Technical Notes

- Navia uses React — standard DOM value assignment won't trigger state updates. Must use the React internal fiber trick or `InputEvent`/`nativeInputValueSetter`.
- Navia selectors live exclusively in `src/constants/navia-selectors.ts`.
- `form-observer.ts` must handle both hash-based and pushState-based SPA navigation.
- The extension can never auto-submit — the user confirmation step is legally important (user is certifying eligibility).
- All selectors should be versioned with a `naviaVersion` field so we can detect drift.
