# PRD-007: Multi-Provider Support

**Status**: `draft`
**Priority**: P2
**Effort**: XL (2–4 weeks)
**Dependencies**: PRD-003
**Last updated**: 2026-03-18

---

## Problem

Navia Benefits is a relatively small FSA administrator. The vast majority of FSA holders use different providers: WEX Health, HealthEquity, Payflex (now WEX), FSA Feds (federal employees), Cigna, MetLife, and others. Limiting the extension to Navia limits the addressable market to a fraction of the ~35 million FSA holders in the US. Multi-provider support is the biggest single unlock for growth.

---

## Goals

1. Support the top 5 FSA portals with auto-fill claim submission (same UX as Navia).
2. Create a provider abstraction layer so new providers can be added without modifying core logic.
3. Auto-detect which provider the user has based on their portal URL.
4. Allow the community to contribute new provider adapters.

## Non-Goals

- Supporting every possible FSA administrator (long tail)
- Integration with native mobile apps of FSA providers
- Supporting HSA providers (different rules, different regulations)

---

| # | As a… | I want to… | So that… |

## Functional Requirements

### FR-1: Provider Abstraction Interface
Define a `FsaProvider` interface that all adapters must implement:
```typescript
interface FsaProvider {
  id: string                    // e.g., 'wex', 'healthequity', 'navia'
  name: string                  // Display name
  portalDomains: string[]       // For URL matching
  claimFormUrl: string          // Direct link to start a claim

  // Scrapers
  scrapeBalance(doc: Document): FsaBalance | null
  scrapeClaimHistory(doc: Document): PortalClaim[]

  // Form filling
  fillClaimForm(claim: Claim, doc: Document): Promise<void>
  attachInvoice(dataUrl: string, doc: Document): Promise<void>
  submitForm(doc: Document): Promise<void>
  detectSubmissionResult(doc: Document): SubmissionResult

  // SPA navigation
  isClaimFormPage(url: string): boolean
  isClaimSuccessPage(url: string, doc: Document): boolean
}
```

### FR-2: Provider Registry
- `src/constants/providers.ts` exports `PROVIDERS: FsaProvider[]`.
- Each provider adapter lives in `src/content-scripts/providers/{id}/`.
- Service worker selects the correct adapter based on the active portal URL.

### FR-3: Supported Providers (v1)
Priority order based on market share:

| # | Provider | Market Share (est.) | Notes |
|---|----------|---------------------|-------|
| 1 | Navia Benefits | small | Already done (PRD-003) |
| 2 | WEX Health | ~25% | Largest third-party administrator |
| 3 | HealthEquity | ~20% | Publicly traded, major employer partner |
| 4 | FSA Feds (FSAFEDS) | Federal employees | High-value demographic |
| 5 | Payflex (WEX) | ~10% | Being absorbed into WEX |
| 6 | Cigna/Evernorth | ~8% | Part of large insurer |

### FR-4: Auto-Detection
- When user opens the extension or visits any FSA portal, detect provider from URL:
  - `wexhealthcloud.com` → WEX
  - `healthequity.com` → HealthEquity
  - `fsafeds.com` → FSA Feds
  - etc.
- Set `AppState.provider` on first detection and prompt user to confirm.
- Store preference so user isn't prompted every time.

### FR-5: Provider Setup Screen
- New onboarding step (see also PRD-009): "Which FSA provider do you use?"
- Shows logo, name, and "Supported ✓" / "Coming Soon" badge for each provider.
- User selects provider → stored in settings → auto-fills future workflows.
- "My provider isn't listed" → link to GitHub issue template to request support.

### FR-6: Provider-Specific Claim Rules
- Each provider has different claim rules that the adapter must encode:
  - Maximum claim amount per submission
  - Whether multiple items can be on one claim
  - Required vs optional fields
  - Accepted file types and size limits
  - Waiting period before re-submission
- `FsaProvider.claimRules` property encodes these constraints.
- `Claim` generation logic (PRD-003 FR-1) queries `claimRules` before building claim objects.

### FR-7: Adapter Testing Framework
- Each provider adapter ships with fixture HTML files (scrubbed portal pages).
- `src/tests/providers/{id}/` contains unit tests for each adapter's scraper and filler.
- CI runs all adapter tests to catch regressions when providers update their portals.

## Technical Notes

- Provider adapters are content scripts — they run in the context of the portal page.
- Service worker determines which provider adapter to inject based on `tab.url`.
- React event injection tricks (from PRD-003) will be needed for every React-based portal.
- WEX and HealthEquity likely use different tech stacks — inspect both carefully.
- Adapter versioning: `provider.version` string allows detecting portal updates.
